近日（2026年6月8日），SAP发布了一份名为《AI-Native North Star Architecture》的架构文档。萨普蓝宝石大会的热度还没散，这份文档就被悄悄放上了SAP Architecture Center。

大多数人扫一眼标题就划走了——"又一份白皮书而已"。

但这可能是2026年对SAP顾问最重要的一份技术文档。因为它回答了一个所有SAP从业者都在问、却没人敢公开说的问题：**SAP自己的AI之前到底行不行？**

答案出人意料地坦诚——**CEO亲口说：不行，我们走偏了。**

---

## 一、最颠覆的事实

在马德里Sapphire大会的闭门媒体会上，SAP CEO Christian Klein被Computer Weekly记者问到一个尖锐问题：SAP是什么时候意识到AI策略不对的？

他的回答，按原话翻译：

> "大概8、9个月前，我们才开始醒悟。我们看了Joule和AI产品的用户反馈——有一些非常正面的评价，但最大的问题是：BTP上的Agent Builder、BDC里的数据内容、还有治理体系，三者根本没有打通。" "你在BTP上选Anthropic构建Agent，得到的结果跟直接用Anthropic没有任何区别。" "**那一刻，我们作为一家公司启动了Code Red。我们把所有工程师召集到一起。** 要展示我们今天发布的东西，真的非常非常艰难。"

一个市值2000亿欧元的公司CEO，公开承认自己的核心AI产品跟"裸用大模型没区别"——这句话的信息量，任何一个做过SAP项目的人都懂。

**Klein的Code Red发生在2025年Q3左右。而North Star架构就是Code Red之后8个月高强度工程化的产物。**

来看这8个月SAP交出了什么：

|   |   |   |
|---|---|---|
|**新能力**|**旧状态**|**颠覆程度**|
|224个AI Agent + 51个Joule助手已部署|Joule只是对话外挂|⭐⭐⭐⭐⭐|
|四层认知核心架构（UX→流程→数据→平台）|Agent Builder、BDC、治理各自独立|⭐⭐⭐⭐⭐|
|Agent拥有独立身份、权限边界、审计轨迹|Agent无身份、无边界、无审计|⭐⭐⭐⭐|
|Agent驱动的ERP迁移（减35%工作量）|人工主导的漫长云迁移|⭐⭐⭐⭐|
|确定性+概率性双路径融合|只有规则引擎或只有LLM幻觉|⭐⭐⭐⭐⭐|
|按业务结果收费（Outcome as a Service）|按订阅/用户数收费|⭐⭐⭐⭐⭐|

## 二、底层逻辑：SAP为什么要"自己革自己的命"？

North Star架构文档里有一句话，我认为是理解整件事的钥匙：

> **"数据是过去十年的护城河。上下文是下一个十年的护城河。"**

翻译成SAP顾问能听懂的话：

|   |   |   |
|---|---|---|
|**维度**|**AI-First（旧SAP）**|**AI-Native（North Star）**|
|AI在哪|嵌在应用里的小功能|跨应用的系统级智能层|
|Agent能看什么|一个应用的数据片段|全业务全景（争议、物流延迟、采购变更同时理解）|
|谁做决策|人 → 看AI建议 → 手动操作|Agent自主执行 → 仅异常路由给人|
|每次交互的结果|一次查询完成|反馈成为学习信号，下次更聪明|
|价值交付|软件即服务（SaaS）|结果即服务（Outcome as a Service）|

**核心公式：**

> **当AI不再"辅助"而是"执行"，SAP的价值锚点从"软件功能"迁移到"业务结果"。顾问不再卖"配置能力"，而是卖"治理能力"。**

这就是为什么Klein说"没有商量的余地"——因为如果不打通数据→流程→治理三层，SAP的AI就是在给Anthropic和OpenAI做嫁衣。客户直接调Claude API就行了，为什么要通过SAP？

## 三、North Star架构：四层认知核心详解

North Star不是一份"放在架子上落灰的白皮书"（原话）。它是SAP正在建造的技术地基。四层架构如下：

### 第1层：用户体验层 —— 从"导航应用"到"陈述意图"

**旧世界**：业务人员打开Fiori → 找事务代码 → 填屏幕 → 跨应用切换 → 手动对账。

**新世界**：对Joule说一句"解决所有可能导致延迟付款的高价值争议，最大化降低DSO"——Joule自动编排财务Agent + 服务Agent + 供应链Agent，协同完成分析→决策→执行→闭环。

这不再是Copilot。Joule Work会在你不在线的时候，主动推送洞察、自动执行日常任务。**工作在你没在看的时候也在推进。**

### 第2层：流程层 —— 应用变成Agent的"能力供应商"

**旧世界**：ERP模块是独立的应用，Agent功能嵌在模块内部，彼此看不到对方。

**新世界**：应用被"拆解"为能力提供方——暴露稳定的API、事件和数据——供Agent跨应用编排。50+个Joule助手调用200+个专用Agent，端到端跑通财务、供应链、采购、HR、客户体验五大领域。

举个例子：**Autonomous Close Assistant**——自主处理日记账、自动对账、自动解决差异，把月结从数周压缩到数天。

### 第3层：基础层 —— 系统从"记录"升级为"理解"

这是整个架构的**认知引擎**：

- **SAP Knowledge Graph**：语义主干。把"请显示逾期订单"这样的自然语言，自动定位到正确的API、筛选参数、构造精确查询。**准确率超过纯模型方案。**
- **SAP Business Data Cloud**：企业的"数据记忆层"。打通异构数据，形成统一语义。
- **模型服务**：SAP自训练模型（如SAP-RPT-1处理结构化业务数据）与第三方模型（Claude等）共存于一个受治理的AI Hub。

**关键一句**："Business Data Cloud让Agent记住企业。Knowledge Graph让Agent理解企业。"

### 第4层：平台层 —— 把"无状态模型"变成"可信任的企业Agent"

这是SAP顾问未来最需要理解的层。也是整个架构的"缰绳"：

- **Agent身份**：Agent成为一等公民主体，有独立身份、限定权限边界、像任何企业角色一样被审计。
- **Harness Engineering**：沙箱化、记忆管理、护栏——用原话说"模型负责推理，但缰绳决定上限。"
- **Agent Gateway**：统一的治理网关，细粒度访问策略（精确到参数级别）、人机回路路由。
- **开放标准**：MCP（模型上下文协议）做工具集成，A2A（Agent-to-Agent协议）做跨组织多Agent协作。

**这不是技术架构文档，这是一份企业治理架构文档。** 它定义了Agent在企业中的法律地位——能做什么、不能做什么、出事了谁负责。

## 四、关键洞察（为什么这份文档跟每个SAP顾问有关）

### 洞察1：SAP在重新定义"ERP顾问"的工作对象

过去50年，SAP顾问的工作对象是"流程"——配置、实施、优化业务流程。

North Star之后，顾问的工作对象将变成"Agent的治理边界"——Config不再是SPRO，而是定义Agent能访问哪些数据、能调用哪些API、在什么条件下必须路由给人。

**Takeda制药的真实案例**：通过自主合规制造，已实现10%生产率提升、25%库存缺货收入损失减少、5%安全库存降低。这不是PPT——是Keynote上SAP COO亲口宣布的生产数据。

### 洞察2：Klein承认"客户等不了3年"

Diginomica报道中提到一个细节：Klein说"我们加速这个旅程是毫无疑问的，到年底客户迁移工作将减少50%。"

但更扎心的是这句：**"CEO和CFO告诉我，他们明天就要AI，不能等到所有现代化改造完成。"**

这意味着SAP顾问面临的不是"AI会替代我吗？"的老问题，而是"客户要AI，但系统还没准备好——谁来填这个坑？"

答案是：**一个既懂SAP又懂Agent治理的新角色。**

### 洞察3：€100M生态基金 = 顾问的变现窗口

SAP斥资1亿欧元设立合作伙伴基金，专门激励Partner帮客户部署SAP AI Agent。

基金覆盖三个层次：

- **Adoption**：激活AI助手并部署
- **Launch**：基于Joule Studio构建自定义Agent
- **Enterprise**：至少3个自定义Agent的生产级部署

Sapphire之前，合作伙伴已经提交了**680个Agent**参加Partner Agent Race。下一个赛段的目标是"生产环境中的企业级Agent"。

**会搭Agent的顾问不缺活。懂治理Agent的顾问会溢价。**

### 洞察4：确定性+概率性 = "AI不能替代规则，但规则也不能限制AI"

North Star的一个核心理念是"双路径"：

- **确定性路径**：合规需要的可预测、基于规则的执行（传统ABAP/配置的世界）
- **概率性路径**：从数据和经验中学习的AI推理

两者不互相替代，而是互补。中间的"胶水"叫**Context Engineering（上下文工程）**——护栏、可观测性、人机回路。

这意味着SAP没有选择"推倒重来"的激进路线（那会让所有顾问失业），而是选择"双轨并行"的渐进路线——**你需要同时理解规则引擎和AI推理，才能做好Context Engineering。**

## 五、SAP顾问的3张新船票

基于以上所有信息，我认为SAP顾问未来的高价值方向有3个：

### 船票1：Agent治理架构师（Agent Governance Architect）

**为什么是新角色**：North Star明确定义Agent为"一等公民主体"——有身份、有权限、有审计。但谁来设计这些治理边界？不是IT安全团队（他们不懂业务流程），不是业务人员（他们不懂技术架构）。

**做什么**：

- 为每个业务领域的Agent设计权限边界（Finance Agent能看哪些公司代码？能调哪些API？）
- 设计异常路由策略（什么情况下Agent必须把决策交给人？）
- 配置Agent Gateway的细粒度访问策略（精确到API参数级别）
- 建立Agent决策可追溯性（审计谁调了什么、为什么做这个决定）

**为什么壁垒高**：需要同时理解SAP授权体系（PFCG/SU01那一套）+ 业务流程 + AI Agent治理概念。三个圈的交集极窄。

### 船票2：业务上下文工程师（Business Context Engineer）

**为什么是新角色**：SAP Knowledge Graph是North Star的"语义主干"。但Knowledge Graph不是天上掉下来的——它需要人把"这个业务到底怎么运转的"编码进去。

**做什么**：

- 梳理客户的业务流程逻辑（SAP Signavio + 人工验证）
- 识别"企业记忆"中的隐性知识（那些从来没被写进文档、但在老员工脑子里的业务规则）
- 设计Agent需要的数据产品（哪些数据源、什么频率、什么格式）
- 验证Agent输出的业务准确性（"差不多对不够好"——Klein语）

**为什么壁垒高**：20年SAP实施经验的价值不是"会配系统"，而是"理解企业到底怎么运转"。这是任何大模型都学不到的——因为它不在公开数据里。

### 船票3：智能体迁移专家（Agent-Led Migration Specialist）

**为什么是新角色**：SAP宣布Agent驱动的迁移工具可以减少35%以上的ERP迁移工作量——通过自动化的系统分析、代码修复、配置和测试。

但别被骗了：**减少35%工作量 ≠ 不需要人。**

**做什么**：

- 验证Agent生成的迁移方案（特别是财务模块——FICO差异处理不是AI能自动判断的）
- 设计迁移中的异常处理流程
- 在迁移过程中同步构建Agent治理体系（不要等迁移完再补治理）
- 帮助ECC客户在承诺云迁移的同时，先获取部分AI场景权限

**为什么壁垒高**：ECC到S/4HANA的迁移本身就是高壁垒技术活。加上Agent因素后，复杂度翻倍——你需要既懂迁移，又懂Agent，还要能预判迁移后Agent怎么跑。

## 六、一个多年年SAP顾问的人的看法

（以下是我的个人观点，不代表任何官方立场——这是这篇文章区别于所有翻译稿的地方。）

### 关于"SAP顾问会被淘汰吗？"

不会。但"只会配置不会思考"的顾问会被重新定价——而且是往下。

North Star架构最核心的一句话是"Model reasons, harness governs"——AI再聪明，也需要一个缰绳。这个缰绳的设计者、维护者、审计者，就是下一代SAP顾问的高价值角色。

但问题是：**你愿意学缰绳工程学吗？**

### 关于"现在该做什么？"

1. **先读懂这份文档**：去SAP Architecture Center下载North Star PDF（免费公开），通读一遍。不需要全部理解——先建立框架感。
2. **找到你的交叉点**：你是FICO顾问？专注Autonomous Close Assistant的治理设计。你是MM顾问？专注供应链Agent的上下文工程。在最熟悉的领域找AI切入点，别贪多。
3. **关注SAP TechEd 2026**：Partner Agent Race的下一个赛段在TechEd。生产级Agent的案例会大量涌现——那是真正的学习素材。

### 关于"SAP这次是真的还是在画饼？"

我的判断：**半真半饼。但真的部分足以改变游戏规则。**

"真"的部分：四层架构是真实的工程方向（不是PPT），Claude已接入、224个Agent已部署、Takeda有生产数据、Agent身份和治理体系已明确。"饼"的部分：Outcome as a Service的商业模式短期内不可能全面落地（合作伙伴生态太庞大，按结果收费会先革了实施伙伴的命）。

但即便如此——**仅"Agent治理"这一个维度，就足以催生一个全新的顾问细分赛道。**
